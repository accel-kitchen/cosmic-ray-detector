宇宙線検出器 V2 — 測定サーバー連携 計画

2026-08-16 時点 / v1・v2 コンソール、cosmicwatch-app、cosmicray-server の 3 リポジトリ調査に基づく

この文書について

v1 / v2 の Web コンソールから、既存の測定サーバー cosmicray-server （http://accel-kitchen.com:3000）へ観測データを送信する機能の設計をまとめる。 参考実装として cosmicwatch-app が同じサーバーへの送信機能を持つが、 そのまま移植しても動かないことが調査で判明した。 本書では、コンソール側の実装設計・サーバー側の更新計画・段階的なロードマップ・未決事項を整理する。

方針（確定済み）
① スキーマは段階式 — Phase 1 は既存 API 互換で先に動かし、Phase 2 でサーバーを拡張して全フィールド対応。
② CORS はサーバー側に追加し、コンソールは file:// のまま使える構成を本命とする。
③ 検出器の識別に device_id / channel を新設し、1 アカウントで複数台・同時計数を区別できるようにする。

実装は行っていない。本書は着手前の設計・合意形成のための文書である。

2. ブロッカー（着手前に必ず解消）

B-1. CORS が一切設定されていない
server.js のミドルウェアは express.json() と静的配信 2 つのみ（:12-14）。 cors パッケージは package.json に無く、node_modules にも入っていない。 Access-Control-* ヘッダを返すコードも存在しない。
影響：送信には Authorization ヘッダと Content-Type: application/json が要るため、 リクエストは必ず preflight される。Express 4 の暗黙 OPTIONS 応答は Allow: しか返さないので preflight が失敗し、本リクエストは 1 度も送信されない。 逃げ道も無い（text/plain にすれば preflight は避けられるが express.json() が本文を解析せず 400、 そもそも JWT をヘッダで送れない）。既存フロントは同一オリジンだから動いているだけ。
B-2. POST /auth/refresh が無認証（認証バイパス）
server.js:185 — app.post('/auth/refresh', (req, res) => {...}) にミドルウェアが無く、 本文の user_id だけで 24 時間有効なトークンを発行する。 さらに GET /list-ids が無認証で全 ID を公開しており、 users.json には role: "admin" の root が存在する。
影響：誰でも管理者トークンを取得できる。新機能でこのエンドポイントを使う前に修正が必須。
B-3. 0 が有効値として扱われない
server.js:289 — if (!event || (!date && !timestamp) || !adc || vol === undefined || !deadtime)。 truthiness 判定のため event: 0（最初のイベント）、adc: 0（ペデスタル以下）、 deadtime: 0（初回）がすべて 400 で拒否される。 加えて :318 の temp || '25.0' により、実測 0 °C が黙って 25.0 に化ける。
影響：正当な測定値が失われ、しかも temp は存在しない測定値を捏造している。

3. サーバー側 Tier 1 — 疎通と安全性の確保

いずれも webserver/server.js への変更。既存クライアント・既存データに対して非破壊。

高工数 小S-01. CORS ミドルウェア

依存追加なしの手書きミドルウェアを server.js:12 に、 express.json() より前・静的配信より前に挿入する。 preflight が本文パーサに届かないようにするため順序が重要。 

const ALLOW_HEADERS = 'Content-Type, Authorization, Idempotency-Key';
app.use((req, res, next) => {
  res.setHeader('Access-Control-Allow-Origin', '*');
  res.setHeader('Access-Control-Allow-Methods', 'GET, POST, PUT, DELETE, OPTIONS');
  res.setHeader('Access-Control-Allow-Headers', ALLOW_HEADERS);
  res.setHeader('Access-Control-Max-Age', '86400');
  if (req.method === 'OPTIONS') return res.sendStatus(204);
  next();
});

* で良い理由：認証は Cookie ではなく Authorization ヘッダで、 クライアントは credentials: 'omit' で送る。したがって credentialed リクエストではなく ワイルドカードが有効になる。Access-Control-Allow-Credentials は設定してはいけない （設定すると * が無効化される）。file:// から開いたページは Origin: null を送るが、 これも * にマッチする。将来 allow-list 方式にする場合は文字列 "null" を明示的に含め Vary: Origin を付ける必要があるため、Tier 1 ではワイルドカードを選ぶ。 Idempotency-Key は Tier 2 で使うので、preflight 定義を二度変えないよう今のうちに許可しておく。

配信方式の対応表（配布方法を規定する）

コンソールの originWeb Serial / BLEfetch http://…:3000
file:// 可 可（Origin: null）— ただし Chrome のバージョン依存。実機確認が必要
http://localhost:PORT 可 可 — 推奨構成
https://…（GitHub Pages 等） 可 不可 — mixed content。CORS では解決できない

つまり CORS を入れても https:// 配信は不可能で、それを可能にする唯一の手段は S-09（TLS 化）である。 Web サイトからコンソールを配る構想があるなら S-09 は必須。

高工数 小S-03. /auth/refresh の認証

app.post('/auth/refresh', authenticateToken, ...) とし、本文の user_id を完全に無視して req.user.id から発行する。

4. サーバー側 Tier 2 — v2 検出器のための拡張スキーマ

4-1. 何が入らないのか

v2 は 13 トークン + ブラウザ時刻を出すが、TSV の行は 7 カラムしかない。 入る場所が無いのは：湿度、気圧、Dig1-3、Ana1-3、エネルギー（keV）、ADC ビット深度、 デッドタイムの単位、同時計数の構成、装置 / ファーム識別、run 識別、タイムゾーン、 そして将来の波形配列（フラット TSV では構造的に不可能）。

(c) は (a)(b) の代替ではなく直交する。1 イベント 1 HTTP はスループットの最大の律速なので、 どの保存形式を選んでもいずれにせよ採用すべき。

4-3. 推奨：(b) + (c) + レガシーミラー

① 新トランスポート POST /v2/ingest/:stationId（バッチ配列）
② 新ストレージ cosmicray-data/<station>/v2/<YYYY-MM-DD>.jsonl（先頭行に format_version のヘッダレコード）
③ レガシーミラー — 受理した v2 イベントを既存 7 カラム .dat にも追記する。 局単位のフラグ legacy_mirror（既定 on）で制御。.jsonl を正、.dat を派生と宣言する

なぜこの組み合わせか：既存エンドポイント・既存ファイル・Python クライアント・ビューアに 文字通り一切手を触れずに済む。ビューアは今まで通り <date>.dat を読むだけで、 ミラー経由で v2 データが初日から表示される。結果としてビューア改修は誰もブロックしない独立タスクになる。 .jsonl 側は dig / ana を今すぐ、波形やスペクトルを将来、 スキーマ交渉なしに載せられる。ミラーが生む「真実が 2 つある」リスクは、 .jsonl を正と宣言し .jsonl → .dat の再生成スクリプトを用意することで 「ミラーのバグ = データ損失」にならないよう封じる。

4-4. 重複排除

バッチ単位：Idempotency-Key ヘッダ。サーバーはキー → 応答の LRU（上限 2000）を持ち、 再送されたら X-Idempotent-Replay: true を付けてキャッシュ応答を返し、何も追記しない。 現実的な重複原因（追記は成功したが応答が失われた）はこれで塞がる。

イベント単位（永続）：全レコードに run_id + seq を持たせる。 LRU はプロセス内なのでサーバー再起動をまたぐ重複は残るが、 この 2 つがあれば解析スクリプト側で常に検出・除去できる。

LRU の永続化は意図的に対象外。ストアが必要になり、フラットファイル構成から大きく逸脱する。 「at-least-once（重複は検出可能）で足りるか」は Q-3 として未決。

4-6. device_id — 局の中のフィールドとして追加する

現在はアカウント ID がログイン名・所有権キー（server.js:283）・ディレクトリ名を兼ねている。 実害は users.json に出ている — sendai のコメントは "coincidence measurement with 2 cosmic watches at aobayamac campus"。 1 アカウント・1 ディレクトリを 2 台の実機が共有していて、データ上は区別できない。

選択肢判断理由
アカウント == 局 を維持し、device_id をレコードのフィールドとして追加 採用 1 局 1 日 1 ファイルが保たれるので、局内の同時計数解析が単一ファイルの逐次走査で済む。N 方向マージが要らない
device_id をディレクトリ階層にする 不採用 同時計数のたびに複数ファイルの時刻マージが必要になる
検出器ごとにアカウント発行 却下 資格情報管理が倍増し、所有権チェックが破綻し、局単位のビューが分断される

device_id はコンソールが生成して crd_upload_v1 に保持する （将来ファーム側がシリアルを公開するならそれを種にする）。人が読む device_label を併せ持つ。 装置一覧は run メタデータから導出して GET /v2/stations/:id/devices で返す。 同時計数のペアリングは run のプロパティ（run.coincidence）とする — これで sendai の 2 台構成がようやく表現できるようになる。

5-4. 資格情報ポリシー（参考実装から意図的に逸脱する点）

規則理由
パスワードは既定で localStorage に書かない。モジュールスコープの変数にタブ生存期間のみ保持する 夜間の連続運転中に 401 が起きたとき、無人で再ログインするために必要。しかし永続化する必要はない
「この PC に保存する」を選んだ場合のみ別キー crd_upload_secret_v1 に保存し、警告を常時表示。チェックを外したら即削除 共用 PC での事故を防ぐ。明示的な選択にする
Base64 / XOR による難読化はしない security theatre であり、保護されているという誤解を生むだけ。本当に必要なら WebCrypto AES-GCM + パスフレーズ（C-14）
JWT は保存するが、それ自体が bearer 資格情報であることを文書に明記。緩和は 24 時間の TTL と「ログアウト」操作 毎回ログインさせないための妥協点を、隠さず書く
file:// では Chrome が全ローカルファイルで localStorage を共有する点を明記 あるローカル HTML に保存した資格情報が別のローカル HTML から見える。既定を「保存しない」にするもう一つの理由

5-5. キュー・再送・バックプレッシャ

局面挙動
ハード上限到達最古を破棄し件数をカウントして UI に出す。ライブ表示は最新が有用であり、正本はローカルにある
一過性の失敗（ネットワーク / 5xx / 408 / 429 / タイムアウト）バッチをキュー先頭へ戻す（batch.concat(queue) — 既存 v2:2441 と同じ書き方。spread の引数上限を避ける）
バックオフ1 / 2 / 4 … 60 秒上限、±20% のジッタ。多数の局が 1 回のサーバー再起動から同時に復帰して同期しないため
試行回数無制限（参考実装の 3 回上限とは異なる）。バッチは先頭に残るだけで、チップが再試行中を示す。ハード上限と組み合わせてメモリは有界、しかし黙って失われることはない
413バッチサイズを半減して即座に再試行（バックオフしない）
400（毒イベント）バッチが 2 件以上なら分割して二分探索、1 件なら拒否リストに記録して先へ進む
401 / 403キューへ戻し、トークン更新を 1 回試行。失敗したらチップを認証エラーにしてキューは保持

切り捨てる経路が存在しないのが要点。データが捨てられるのはハード上限超過の一箇所だけで、 それは必ずカウントされ画面に出る。

重複判定を持たない理由

参考実装は 1 イベントずつ撃って何が着弾したか分からないため、送信済みキーの Set を無限に持っていた。 本設計では、キューが厳密な FIFO で in-flight バッチが常に 1 つなので、 1 イベントが 1 試行につき高々 1 回しか送られない。 残る重複要因（追記後に応答が失われた）はサーバー側の Idempotency-Key と 永続的な (run_id, seq) で処理する。コンソールは Set を一切持たない。

高レート時のバックプレッシャ

互換モードのスループットは概ね「並列数 ÷ RTT」で、RTT 60〜200 ms なら毎秒 20〜60 件が上限。 v2 のバッチ送信（200 件 / リクエスト）なら毎秒数千件まで上がる。 ソフト上限を 30 秒以上超え続けたら滞留警告を出し、 ユーザーが送信レートを手動で下げるのを促す（ローカルには全件残る）。 間引いた件数は破棄件数と別カウンタにする — 間引きをデータ損失と誤認させないため。

自動間引き（滞留が続いたら勝手にレートを下げる）は初版では入れない。 暗黙のデータ間引きはユーザーを驚かせる。Q-5 として未決に回す。

5-6. タイムスタンプ

サーバーのパーサ（server.js:301-310）は文字列を - で分割して6 要素以上を要求する。 YYYY-MM-DD-HH-MM-SS.ffffff のローカル時刻でなければならない。 ISO-8601 を送ると 3 要素にしかならず、else 分岐に落ちてファイル名がサーバーの UTC 日付になり、 2 列目が 2026-08-16-2026-08-16T12:00:00.000Z のような壊れた値になる。

アンカー方式

v2 には 2 つの時計がある。pc_timestamp は壁時計だが USB / BLE のバッファでジッタが乗る （まとめて届いた行が同じ値になる）。timestamp_us は間隔が正確だが壁時計を持たない。 どちらか一方では正しくないので、デバイスの µs 間隔をブラウザの壁時計にアンカーする。 

function uploadClockUs(ev) {
  const u = state.upload;
  const devUs = ev.timestamp_us;
  const reboot = devUs < u.anchorDevUs || ev.count < u.anchorCount;
  const derived = u.anchorWallUs + (devUs - u.anchorDevUs);
  const drift = Math.abs(derived - ev.pc_timestamp * 1000);
  if (!u.anchorWallUs || reboot || drift > 5_000_000) {   // 5 秒
    u.anchorWallUs = ev.pc_timestamp * 1000;
    u.anchorDevUs  = devUs;
    u.anchorCount  = ev.count;
    return u.anchorWallUs;
  }
  return derived;
}

結果として、イベント間隔はデバイスの水晶発振器由来の µs 分解能を保ちつつ、 絶対時刻はブラウザの壁時計に固定される。再起動や NTP による時刻跳躍では自動で再アンカーされる。 参考実装が getMilliseconds() * 1000 で下 3 桁を捏造していたのとは異なり、 .ffffff の桁に物理的な意味がある。

v1 は timestamp_ms なので同じ方式を ×1000 で適用する。 下 3 桁は 000 になるため、「ミリ秒の真値をマイクロ秒の書式で書いている」ことを文書に明記する。

タイムゾーンの穴

サーバーはどこにもタイムゾーンを記録していない。 書き込み側はクライアントのローカル日でファイル名を決めるのに、latest-data（:339）は UTC で日を決める。 JST では毎日 00:00〜09:00 が食い違う。異なるタイムゾーンの局同士は比較できず、 DST 地域では毎年「曖昧な 1 時間」と「存在しない 1 時間」が生じる。

対策の順序：

  1. コンソールは互換モードでも常に tz（Intl.DateTimeFormat().resolvedOptions().timeZone）、 tz_offset_min、timestamp_utc を送る。現ハンドラは余分なキーを無視するので無害
  2. Tier 2 では t_utc_us（整数 epoch µs）を正とし、ローカル文字列は派生の便宜フィールドに落とす
  3. Tier 1 の即効策として latest-data の日ファイル選択を書き込み側に揃える（S-08）
  4. 文書に明記：既存 .dat の時刻はタイムゾーン不明のローカル時刻。過去ファイルは遡って直せず、局ごとの注記でしか救済できない

オフラインPOST 自体を行わず、バックオフの試行回数も消費しない。online イベントで再開
測定中のトークン失効失効 5 分前に更新。失敗しセッションのパスワードがあれば無言で再ログイン。どちらも駄目なら認証エラー表示のままキューを保持
同一局を 2 つのタブから送信サーバーは許可する。run_id で区別される。文書で注意喚起する
NTP による時刻跳躍ドリフト検知で再アンカー。イベント間隔はデバイス時計由来なので影響を受けない
一時停止中（state.paused）イベント自体が生成されないので何も積まれない。自動保存と同じ挙動

5-9. v1 の既存不具合（C-11、同時に直す）

v1 の flushAutoSave()（v1/index.html:1924）には、v2 が持つ 2 つの防御が両方とも無い。
① 再入ロックが無い — v2 の as.flushing（v2:2401）に相当するものが無く、 1 秒間隔の呼び出しが前回の書き込み完了前に走ると、同一 FileSystemWritableFileStream に対して 並行に seek / append してファイルが壊れる。
② 書き込み失敗時にバッチを戻していない — :1950 で as.pending.splice(0) により キューから取り出した後、:1964-1968 の catch はエラー表示だけで batch を再投入しない。v2 は v2:2441 で as.pending = batch.concat(as.pending) と戻している。 v1 では一過性の書き込み失敗がそのままイベントの永久喪失になる。
さらに v1 の disconnect()（:1518）には切断時の最終 flush が無い。

これらはサーバー連携とは独立した既存バグだが、v1 にアップローダを載せる際に同じファイルの 同じ関数を触るため、同時に直すのが自然。優先度は高。

6. カラムずれの解消とビューア対応

6-1. 現状の実害

writer は 7 カラムを書く（server.js:317-318）のに、reader は両方とも 4 カラムで分解している （server.js:350 の latest-data、server.js:457 の /api/data）。 

const [adc, timestamp, vol, deadtime] = line.split('\t');
API のキー実際に入っている値
adc1 列目 = EVENT カウンタ
timestamp2 列目 = 日時文字列 （これだけ正しい）
vol3 列目 = TIME（µs）
deadtime4 列目 = 本当の ADC 値

5〜7 列目（SiPM、本当のデッドタイム、温度）はJSON API からは到達不能で、 生ファイルをダウンロードするしかない。 ビューアの ADC ヒストグラムは cosmicray-viewer/app.js:401 が parseInt(point.deadtime) を読んでいるため偶然正しく動いている。

直近 2 コミットが writer だけを変えて reader を放置したことでこのずれが入った。 新しいクライアントがフィールド名を信じると必ず踏む罠なので、両側を触るなら最初に直すべき箇所。

6-2. 非破壊の 3 段階移行

  1. 共通パーサ parseLegacyDatLine(line) を導入。 列数で分岐する（4 → 旧形式、7 → 現行）。古いファイルには本当に 4 カラムのものが残っているため、 幅の判定は必須。latest-data・/api/data・.jsonl → .dat 再生成の 3 箇所で共用する
  2. レスポンスは加算的に。既存 4 キーを現在の（誤った）意味のまま残し、 正しい名前のキーを追加する。既存ビューアは無改修で動き続ける 
    { "timestamp": "…", "adc": "1", "vol": "…", "deadtime": "2048",
  "event": 1, "datetime": "2026-08-16-21-13-20.123456", "time_us": 987654321,
  "adc_value": 2048, "sipm_mv": 1650.427, "deadtime_ms": 1234, "temp_c": 23.4 }
  3. ビューアを切り替えてから旧キーを非推奨化。 app.js:401 を point.adc_value ?? point.deadtime に変え、 SiPM / 温度 / デッドタイムのパネルを初めて追加できるようになる。 告知期間（例：2 リリース）の後に旧キーを削除

6-3. v2 データのビューア対応（V-02）

レガシーミラー（S-15）があるおかげで、これは誰もブロックしない独立タスクになる。

  • GET /api/files/:id に .jsonl を含める
  • GET /api/v2/data/:id/:date（device_id と時間範囲でフィルタ可能）
  • UI：装置セレクタ、湿度 / 気圧 / Dig / Ana の系列、run メタデータのパネル、 run.tz に基づく UTC / ローカル切替

8. 未決事項（人が判断する必要がある）

#問いなぜ判断が必要か
Q-1 サーバーを TLS 化するか（S-09） 入れなければコンソールを https:// で配信することが永久に不可能。 file:// と http://localhost だけが選択肢になり、GitHub Pages も LAN の HTTPS キオスクも使えない。配布方法全体を規定する
Q-2 /auth/refresh は期限切れトークンを猶予期間内で受け付けるか 厳格にする（推奨）と、24 時間を超える無人運転はパスワードをメモリかディスクに持つ必要がある。セキュリティと無人運転の trade-off
Q-3 at-least-once（重複は検出可能）で足りるか、exactly-once が要るか 後者は冪等性状態の永続化が必要で、現在の「DB 無し・フラットファイル」構成から大きく逸脱する
Q-4 互換モードの deadtime は µs（v2 ネイティブ）か ms（CosmicWatch 規約）か 本設計は ms 変換。既存の解析が µs 前提なら過去データとの比較が壊れる。物理側の確認が必要
Q-5 滞留が続いたときの自動間引きを許すか 現状は手動のみ。暗黙にデータを間引くと、サーバーを完全な記録と考えている人を誤らせる
Q-6 v2 の vol 列に adc/4095*3300 mV の計算値を入れてよいか 測定値ではない。空にする方が誠実だが、既存ビューアの期待を壊す
Q-7 本番 pm2 の再起動権限は誰が持つか Phase 0 は全項目が本番再起動を伴う。特に S-05 の鍵更新で全ユーザーが 1 回再ログインになる
Q-8 .jsonl の保持期間とディスク予算 TSV の 2〜3 倍 + レガシーミラー。ローテーションが無い単一 VM のフラットファイル構成では高レート時に急速に増える
Q-9 既存 .dat の ADC ビット深度をどう扱うか v1 NANO 0–1023 / v1 ESP32-S3 0–4095 / v2 0–4095 が事後に判別できない。局ごとの config.json への注記が唯一の救済
R-1 cosmicwatch-app はマージ競合中でビルドできない 実行可能な参照として扱わないこと。test.html と server-README.md のみを見て、既知欠陥は意図的に踏襲しない
R-2 file:// + Origin: null + http:// fetch は Chrome バージョン依存 現場の Chrome で実機確認してから file:// 対応を約束すること。代替は http://localhost + 小さな静的サーバーだが、非技術者向けの手順書が別途必要になる
R-3 レガシーミラーは同じ測定の 2 コピーを作る .jsonl が正・.dat が派生であることの明文化と再生成スクリプトが無いと、両者が静かに乖離する

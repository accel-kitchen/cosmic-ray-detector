高工数小X-1. v1.html は Chart.js を読み込めないと、初期化が途中で止まって保存も動かない

現象：v1.html は Chart.js を CDN（cdn.jsdelivr.net）から読む（v1.html:7–9）。読み込めないと initCharts() が TypeError で落ちる。DOMContentLoaded の中では、このあとに renderView()、ResizeObserver、そして setInterval(flushAutoSave) と setInterval(updateRateChart) が続くので、どれも実行されない。

確認：ブラウザ上で Chart を無くした状態を作り、initCharts() と processLine('1 1000 120 25.10 0 24.3') を呼ぶと、前者は Cannot read properties of undefined (reading 'defaults')、後者は (reading 'data') で失敗した。イベント自体は state.events に入るが、統計・表・グラフを更新する処理は、エラーより後ろにあるので走らない。

v1 担当も、スクリプトタグを外した iframe で再現した（同じ問題を V-4 として報告）。USB の場合は、読み取りループの catch（1755）が、最初のイベントで disconnect() を呼ぶ。書き出しのボタンが有効にならない（2605 より前に例外で止まる）。

影響：検出器は、インターネットにつながらない実験室や屋外で使うことが多い。そこで v1.html を開くと、数字もグラフも動かず、自動保存の定期書き込みも始まらない。保存先を選んでも何も書かれないのに、画面には何も出ない。v2 の記録画面は自前の canvas なので、この問題はない。

修正案：

  • 最小: initCharts() を try/catch で囲み、失敗しても残りの初期化（定期処理）を続ける。processLine() のグラフ更新も if (histogramChart) で守り、グラフが無いときは画面上部に「グラフを読み込めませんでした。数字と保存は動いています」と出す。
  • 根本: Chart.js をリポジトリに置いて（assets/vendor/chart.umd.min.js、約 200 KB）相対パスで読む。あわせてフォントの CDN も、ローカルに置くか、フォールバック指定を確認する（フォントは失敗しても表示は崩れない）。

根拠: v1.html:7–9、3610–3674（DOMContentLoaded 内の呼び出し順: initCharts 3654 → renderView → ResizeObserver → setInterval 3671, 3674）。実行して確認。

5.2 課題（中）

中工数小V-2. USB を普通に切断すると、ポートが開いたままになる（実機では未確認）

現象：port.readable.pipeTo(decoder.writable)（v1.html:1739）と encoder.readable.pipeTo(port.writable)（1591）の Promise を捨てている。disconnect()（1718–1729）は、reader.cancel()、writer.close()、port.close() を順に呼ぶが、パイプが終わるのを待たない。ストリームがまだロックされたまま port.close() を呼ぶと、Chrome は Cannot cancel a locked stream で拒否する。

確認：本物のストリームの動作を使い、close() がロック中のストリームを拒否するモックで試すと、3 回中 3 回、拒否された（読み取り側の遅延 0 / 5 / 20 ミリ秒）。拒否されると state.port が残り、catch（1730）はログを出すだけ。次の「もう一度つなぐ」は open() で失敗し、「ほかのアプリを閉じてください」（1574）と、的外れな案内が出る。ページを再読み込みするとデータが消える。実機で起きるかは、確認が必要。Web Serial の標準的な書き方（パイプの Promise を保持して待つ）に反している。

修正案：パイプの Promise を保持し、順に待つ。手順ごとに try/catch を分ける（v2 は core.js:626–646）。

const readableClosed = port.readable.pipeTo(decoder.writable);
const writableClosed = encoder.readable.pipeTo(port.writable);
// disconnect:
try { await reader.cancel(); } catch (_) {}
await readableClosed.catch(() => {});
try { await writer.close(); } catch (_) {}
await writableClosed.catch(() => {});
try { await port.close(); } catch (_) {}

根拠: v1.html:1574, 1591, 1718–1735, 1739。モックで 3/3 再現（v1 担当）。

中工数小V-5. BLE のコマンドを同時に送ると、後ろのものが捨てられる（オシロを開くと「ファームが対応していない」と出る）

現象：BLE の sendCommand は、await rxChar.writeValue(…) を直接呼ぶ（v1.html:1763–1783）。scopeEnter() は、SET_SCOPE_RATE、SET_SCOPE:ON、GET_SCOPE を、待たずに続けて呼ぶ（3278–3281）。GATT は一度に 1 つの操作しか受けないので、2 つ目以降は拒否され、catch に握りつぶされる（1780）。

確認：1 操作ずつしか受けない GATT のモックで試した（v1 担当）。最初の 1 つしか届かず、SCOPE: の応答が来ない。2.5 秒後（3282）に、「ファームがオシロに対応していません」と誤って表示され、15 秒後の keepalive が SET_SCOPE:ON を 1 つだけ送るまで続く。素早く 2 つ操作したときも同じ。

修正案：コマンドを Promise の鎖で 1 つずつ送る（v2 の core.js:683–688 と同じ）。

let cmdChain = Promise.resolve();
function sendCommand(cmd) {
  if (state.transport === 'demo') { demoCommand(cmd); return Promise.resolve(); }
  cmdChain = cmdChain.then(() => sendCommandNow(cmd)).catch(() => {});
  return cmdChain;
}

根拠: v1.html:1763–1783, 3263, 3278–3286。モックで再現（v1 担当）。scopeEnter の呼び出しの並びは筆者が確認した（USB では writer.write がキューに入るので影響しない。BLE のみ）。

3. 新しい課題と修正案（高・中）

高工数小N-1. 自動保存の書き込み中に切断すると、別名のファイルに書き、最後の書き込みも飛ばされる

現象：flushAutoSave() は、書き込みの最中だと強制（force）でもすぐ戻る（3610）。書き込み中の処理は、await のたびに as.prefix と as.dirHandle を読み直している（3592）。

影響：

  • 保存形式が「両方」で、.dat の書き込み中（ファイルが大きいと数秒かかる）に切断すると、切断側の強制書き込みは何もせずに戻る。続いて endAutoSaveSession() が接頭辞を null にする（2694）ので、そのあとの .csv は null_2026-10-06.csv に書かれる。日付をまたぐバッチなら、形式が 1 つでも起こる。
  • 書き込みの最中に届いたイベントはキューに残ったまま次の接続に持ち越され、次の基板の名前のファイルに入る。
  • 書き込みの最中にフォルダを選び直すと（3495）、残りが新しいフォルダに書かれ、書き込み件数のカウンタも途中でリセットされる。

ファイルが大きいほど 1 回の書き込みが長くなるので、長時間の測定ほど起こりやすい。強制書き込みが飛ばされるのは以前からだが、null_ のファイルは前回の修正（R-2 c の接頭辞の固定）で入った問題。

修正案：書き込み先を最初に変数へ固定し、強制書き込みは実行中のものが終わるのを待ってから残りを書く。

let autoSaveRun = null;   // 実行中の書き込み

async function flushAutoSave(opts) {
  const force = !!(opts && opts.force);
  if (as.flushing) {
    if (!force) return;
    await autoSaveRun;          // 終わるのを待ってから、残りを書く
  }
  ...
  const dir = as.dirHandle, prefix = as.prefix;   // 途中で変わっても混ざらない
  autoSaveRun = (async () => { /* flushAutoSaveFormat(fmt, dir, prefix) */ })();
  await autoSaveRun;
}

根拠: 3592, 3604–3646, 2646, 2694, 3495–3500。

} else if (strcmp(cmd, "RESET") == 0) {

中工数小N-3. 「再送」で、送信中のバッチが二重に送られる（R-3 の残り）

現象：flushUpload() は送る前にバッチをキューから取り出し（4092）、応答が返ってから uploaded を付ける（4105）。uploadResend() は「キューにあるもの」だけを重複とみなす（4281）ので、送信中の最大 20 件をもう一度積む。

影響：回線が遅く未送信が溜まっていると、1 秒ごとの送信のほとんどの時間でバッチが送信中になる。ちょうど再送ボタンを押したくなる状況で、サーバー側の行が重複する。

修正案：送信中のイベントを集合で持ち、再送の除外に加える。

const batch = u.queue.splice(0, UPLOAD_LEGACY_BATCH);
u.inFlight = new Set(batch);
try { ... } finally { u.inFlight = null; }

// uploadResend()
const already = new Set(u.queue);
if (u.inFlight) for (const ev of u.inFlight) already.add(ev);

根拠: 4092, 4105, 4277–4298。

中工数小N-4. デモを止めた直後の書き込みが、普通のファイルに入ることがある

現象：disconnect() はデモを止めて demo.on を false にしてから（2642）、最後の書き込みをする（2646）。ファイル名の DEMO_ とヘッダの注記は、書き込みの時点の demo.on で決まる（3541, 3558）。

影響：接頭辞は BLE 名などの応答を待ってから固定するので（3615–3623）、デモ開始から 1〜2 秒以内に切断すると、最初の書き込みがこの最後の書き込みになり、合成データが CosmicRay_日付.dat に注記なしで入る。同じ日に実機で測ったファイルがあれば、そこに混ざる。書き込みが失敗してキューに残った場合も、次の実機の接続のファイルに入る。

以前からあった問題（修正前は、デモを切断するたびに最後の 1 秒分が普通のファイルに入っていた）。接頭辞の固定で起こる範囲は狭まったが、残っている。

修正案：デモかどうかは、書く時点の状態ではなくイベント自身の印（ev.demo）で決める。flushAutoSaveFormat() で日付と同じように ev.demo でも振り分け、デモのものは DEMO_ 付きのファイルと注記入りのヘッダにする。

根拠: 2642–2646, 3537–3558, 3615–3623。

中工数小N-5. 「このセッション」の計数率に、別の基板の値が混ざる

現象：計数率の区間は切断で閉じるが、合計（state.rate.done）は「データを消去」でしか 0 に戻らない（5737）。画面は「検出器の計数（このセッション）」（1432, 1708）、description.md は「この接続セッションの値」（description.md:280）と書いている。

影響：基板 A で測ったあと、消去せずに基板 B につなぐと、平均計数率・経過時間・デッドタイムが A と B を足した値になる。総イベント数も同じく累計なので数字どうしは矛盾しないが、表示の「セッション」とは意味が違う。

修正案：どちらかに揃える。

  • 「データを消去から」の累計と定義し直し、表示と description.md の文言を直す。基板アドレス（BTADDR:）が前と変わったら、画面上部に「別の基板です。消去してから測ることを勧めます」と出す。
  • または、新しく接続した基板のアドレスが前と違えば、区間の合計を自動で 0 に戻す。

根拠: 3351–3375, 5737, 1432, 1708, description.md:280。

中工数小N-6. オシロのタブを開いたままにすると、計数が止まり続ける（R-6 の残り）

現象：オシロのタブを開いている間、ページは 15 秒ごとに keepalive を送り（4902–4912）、ファームの 60 秒の安全装置を延長し続ける。

影響：オシロを見たままタブを切り替えずに夜通し放置すると、朝まで計数がない。ヘッダの「計数停止中」で気付けるようにはなったが、離席していれば見えない。安全装置が効くのはページが閉じた・寝た場合だけ。

修正案：オシロのタブで一定時間（例: 10 分）操作がなければ、解析タブに戻して計数を再開する。戻したことは画面上部に出す。あわせて、ヘッダの「計数停止中」に停止してからの経過時間を出す。

根拠: 4879–4912, fw:240, 1317。

高工数小R-1. 計数率の計算が誤っている

現象：計数率を「ブラウザで受信したイベント数 ÷ 最後のイベントの基板時刻」で計算している（2827–2838）。基板時刻は起動か RESET からの経過時間で、デッドタイムも差し引いていない。

影響：

  • 動作中の基板に Clear せずに接続すると、受信数は少ないのに経過時間は長いため、ほぼ 0 cps と表示される。screenshot1.png が実例で、Total Events 4、Elapsed 07:02:20、Avg. Rate 0.000 と写っている。
  • オシロを使ったあとや、記録を一時停止したあとは低く出る。オシロの説明文（1281, 1529）には「滞在時間はデッドタイムに計上されるので計数率は正しい」とあるが、ページ側の計算はそうなっていない。
  • BLE 名の変更で基板が再起動すると（fw:723）、時刻だけが 0 に戻るので逆に高く出る。
  • 上限の 100 万件を超えると、件数は頭打ちのまま時間だけ伸びるので、計数率が下がっていく。

修正案：ファームの OLED 表示（fw:1645–1652）と同じく、基板側のカウンタ・時刻・デッドタイムの差分を使い、ライブタイムで割る。

const first = events[0], last = events[n - 1];
const counts = last.count - first.count;
const liveUs = (last.timestamp_us - first.timestamp_us)
             - (last.deadtime_us  - first.deadtime_us);
const rate    = liveUs > 0 ? counts / (liveUs / 1e6) : 0;
const rateStd = liveUs > 0 ? Math.sqrt(counts) / (liveUs / 1e6) : 0;

count が減ったとき（RESET や再起動）は区間を切り替え、区間ごとの計数とライブタイムを足し合わせる。経過時間と合計デッドタイムの表示もセッション基準にそろえる。

根拠: 2827–2838、2848（合計デッドタイムも起動時からの累積のまま）、fw:1645–1652、screenshot1.png。

高工数小R-3. 「再送」でサーバー上のデータが重複する

現象：uploadResend() は「キューにない、メモリ上の全イベント」を積み直す（3594–3608）。送信に成功したかどうかを記録していないので、送信済みのイベントも再び送る。

影響：サーバー側の行が重複する。キューの上限は 50,000 件で古いほうから捨てるため、上限に達した状況で再送すると、本来送りたかった古い未送信分が捨てられ、送信済みの新しい分だけが残る。

修正案：成功したイベントに印を付け、再送の対象から外す。

// flushUpload() の結果処理
if (r && r.ok) { batch[i].uploaded = true; ok++; continue; }
// HTTP 400 で拒否されたもの
batch[i].rejected = true;

// uploadResend()
const add = state.events.filter(ev => !ev.uploaded && !ev.rejected && !already.has(ev));

根拠: 3437, 3443–3449, 3592–3608。

高工数小R-4. PWM（コンパレータしきい値）を操作する UI がない

現象：ファームは SET_PWM:<0-255>、GET_PWM、AUTO_PWM[:target] に対応していて、応答は PWM:<duty>（fw:514–533, 1070–1072）。ページにはこれらを送る経路がなく、PWM: 行を処理する部分もないため、応答は 13 列のイベント行チェックで捨てられる（2686）。

影響：Digital/Dual モードのボタンは押せるが、コンパレータのしきい値を校正できない。ファームは Digital に切り替えると「AUTO_PWM を実行して」と促すが（fw:583）、ページからは実行できない。あわせて、Duty の表示は「/ 1023」（1263, 1511）だが、ファームの上限は 255（fw:94）。

修正案：しきい値の設定欄に、Duty の入力、Set/Get、Auto PWM ボタンを追加する。processLine() に PWM: の処理を加え、表示を「/ 255」に直す。接続時の状態取得（2337–2359）にも GET_PWM を加える。idea.html の C-2 と同じ提案。

3. 課題と修正案（中）

中工数小R-5. BLE の書き込みが衝突する

現象：scopeEnter() は 2 つのコマンドを、前の送信を待たずに続けて送る（4138–4139）。BLE の GATT は同時に 1 件しか書き込めず、Chrome は書き込み中の次の書き込みを「GATT operation already in progress」で拒否する。拒否されてもエラーは console に出るだけ（2330–2332）。

影響：SET_SCOPE:ON が失われると、オシロは「トリガ待ち」のまま止まる。設定ボタンを素早く続けて押した場合も同じことが起こる。

修正案：送信を 1 本の待ち行列にまとめ、1 件ずつ送る。非推奨の writeValue() は writeValueWithResponse() に置き換える。

let cmdChain = Promise.resolve();
function sendCommand(cmd) {
  cmdChain = cmdChain.then(() => sendCommandNow(cmd)).catch(() => {});
  return cmdChain;
}

こうすれば、接続時の setTimeout を何段も並べた状態取得（2337–2359）も、最初に 1 回待ったあと順に送るだけで済む。

中工数小R-6. オシロの状態がページとファームでずれる

  • オシロのタブを開いたまま USB/BLE で接続しても、SET_SCOPE:ON を送らない。デモ接続では送っている（4721–4725）。
  • 接続時の状態取得に GET_SCOPE がない（2337–2359）。タブを閉じたときの OFF 送信（4177–4179）は非同期で、届く保証がない。届かないと、次に接続しても計数が止まったままで、そのことに気付けない。
  • オシロのタブを開いたまま放置すると、その間ずっと計数が止まる（夜通しの測定がすべて失われる）。

修正案：USB/BLE の接続処理の最後に if (scope.active) scopeEnter(); を加える。状態取得に GET_SCOPE を加え、タブが開いていないのに SCOPE:ON が返ってきたら OFF を送る。オシロ動作中はヘッダに「計数停止中」と目立つ表示を出す。ファーム側にも、一定時間コマンドが来なければ自動で OFF に戻す安全装置があると安心。

中工数小R-7. BLE 名の長さ制限がファームと合っていない

現象：ページは 24 文字まで入力を許す（697, 4846）。ファームの BLE 名の上限は 24 文字（fw:175）だが、コマンドの受信バッファは 31 文字まで（fw:268, 343, 744）なので、SET_BLENAME: の 12 文字を引くと、送れる名前は実質 19 文字まで。

影響：20〜24 文字の名前は知らせなしに切り詰められて保存され、基板が再起動する。ページは送信前に 24 文字のまま localStorage に保存する（4851）。再起動前に返る BLENAME: を受け取れなかった場合、BLE 接続時の名前フィルタ（2189–2191、完全一致）で基板が見つからなくなる。

修正案：ページ側の上限を 19 文字にする（maxlength と正規表現の両方）。localStorage への保存は BLENAME: を受け取ってから行う。ファーム側のバッファを 48 バイト程度に広げる方法でもよい。

中工数小R-8. 接続に失敗しても画面に何も出ない

現象：connectUSB() と connectBLE() は、失敗すると console.error するだけ（2151–2153, 2223–2225）。

影響：よくある原因の「Arduino IDE のシリアルモニタがポートを使っている」で接続できなくても、ボタンを押して何も起きないように見える。

修正案：エラーを画面上部の警告欄に出す。NotFoundError（利用者がキャンセルした）は無視する。NetworkError や InvalidStateError のときは「他のアプリがポートを使っていないか確認してください」と案内する。ポートを開いたあとで失敗した場合は、ポートを閉じてから戻る。

中工数小〜中R-9. 認証情報の扱い

  • 入力例が http://accel-kitchen.com:3000（610, 1160）で、ログイン時のパスワードを平文の HTTP で送る（3288–3291）。接続できないときの案内文（1193）も、http で開くよう勧めている。
  • 「パスワードを記憶」を切っていても、認証トークン（JWT）は常に localStorage に保存される（3089）。トークンが有効な間は、それだけでアップロードできる。

修正案：サーバーを HTTPS にし、入力例と案内文もそれに合わせる。「記憶しない」ときは、トークンを sessionStorage に置くか、保存しない。

中工数中R-10. BLE の自動再接続がない

現象：BLE が切れると、onBLEDisconnected() で切断状態に戻るだけ（2240–2251）。

影響：夜通しの BLE 測定で一瞬でも電波が途切れると、そこで記録が止まる。

修正案：利用者が切断したのでなければ、device.gatt.connect() を 1, 2, 4, …, 30 秒の間隔で再試行し、通知の購読もやり直す。自動保存のセッションは引き継ぎ、ヘッダには「再接続中」と出す。

中工数小R-11. 送信データの時刻がぶれる

現象：時刻の換算（uploadClockUs()）を、キューに積んだときではなく送信するときに行っている（3168）。この換算は「基板時刻が前回より戻ったら再起動とみなして基準を取り直す」（3126）。

影響：送信に失敗して古いイベントを再送すると、基板時刻が戻ったと判定されて基準が取り直され、その後のイベントの時刻がぶれる。

修正案：到着順に enqueueUpload() の中で一度だけ計算し、ev.wall_us に確定させる。送信時はその値を使う。

中工数中S-1. 5,047 行が 1 ファイルに入っている

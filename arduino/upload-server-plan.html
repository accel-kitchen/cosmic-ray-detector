2. 設計方針

2-1. Console を変えず、互換 API から始める

Console（core.js の uploadLogin 〜 flushUpload）は、すでに次の契約で話す。新サーバーが同じ契約を実装すれば、URL 欄に入れるだけで動く。

エンドポイントConsole が送るものConsole が期待するもの
POST /auth/login{id, password}{token}（JWT。exp を読んで期限を判断）
POST /setup-idBearer + {id, comment, gps_latitude, gps_longitude, created_at}2xx。何度呼んでも成功する（毎回のログインで呼ぶ）
POST /auth/refreshBearer（本文は {}）{token}
POST /upload-data/:idBearer + 1 イベント: event, timestamp, time, adc, vol, deadtime, temp, timestamp_utc, tz, tz_offset_min, run_id, device_label（4 並列・1 回に最大 20 件）2xx = 受理。400 = 永久に不正（Console は捨てて先へ進む）。401/403 = 再認証。それ以外（429・5xx）= 再送
契約上の注意：ステータスの使い分けが Console の挙動を決める。400 を一時的な不具合に使うとデータが捨てられ、永久に不正なものに 5xx を使うと再送が止まらない。 サーバーが受け取る id は局 ID（登録時に参加者が決めるユーザー名）で、メールアドレスではない（Console の入力欄は id しか持たない）。
Console を変えない限り、本人が知らないままコメントが公開される。 Console は毎回のログインで /setup-id に settings.fileComment（ローカル保存用のコメント）または装置ラベルを送る（core.js:2775）。 そのため、/setup-id が受け取るコメントと装置ラベルは非公開で保存し、公開用の説明（局の紹介文）はマイページだけで設定できるようにする。公開 API はマイページの紹介文だけを返す。

v2 のバッチ API・run メタデータ・全フィールド対応は、server-plan.html の §4（POST /v2/ingest/:id、.jsonl、Idempotency-Key、device_id）の決定をそのまま再利用し、設計し直さない（Phase 6）。

2-2. 技術構成

要素選択理由
実行環境Node 22（VPS に v22.14.0 が入っている）+ Express既存の資産と運用知識を使える。TypeScript は使わず、追加の建て付けを増やさない
アカウント・局・同意・トークンSQLite（better-sqlite3 の配布済みバイナリ）自己登録・メール認証・再設定・削除・同意の記録は、users.json では扱いきれない。node:sqlite は実験段階なので使わない
イベント本体局ごと・日ごとの追記専用 .jsonl（正）+ SQLite に時間別の集計（ビューア用）。日付の境界は UTC（timestamp_utc で切る）server-plan.html §4-3 の推奨を踏襲。バックアップ・解析が容易で、集計が壊れても再生成できる。UTC で切るのは、旧サーバーのタイムゾーン問題を持ち込まないため
パスワードscrypt（N=2^17, r=8, p=1）。ハッシュ 1 件あたり約 128 MiB を使うので、同時に走らせるのは 2 件までに制限し、残りは待たせる。パラメータはハッシュ自体に入れるので、あとから上げられる。旧 bcrypt ハッシュの検証は未実装で、Phase 4（移行）で足す（ログイン成功時に scrypt へ再ハッシュ）Node 22 / 24 の標準の crypto だけで済む（argon2 は Node 24.7 以降）。N=2^17 は OWASP が、Argon2id が使えないときの scrypt の最低ラインとして示す値。VPS のメモリ（R-N1）を見て同時実行数を決める
トークンJWT HS256、24 時間（Console の /auth/refresh 前提と合わせる）+ ユーザーごとの失効番号パスワード変更・アカウント停止で既存トークンを無効にできる
Cookieどこにも使わない（Bearer のみ）CORS を * にしても、認証情報が自動で付かない
公開ページ登録・認証・再設定・マイページ・ビューア・地図を、同じサーバーから静的に配信同一オリジンなので CORS の問題が出ない。Console だけが別オリジンから API を呼ぶ

未検証の前提：1 局あたりのイベント率と参加局数は不明（§8 の Q-N3）。ディスク予算とローテーションはこの値で決まるため、旧データ（sendai など）の実測値から見積もる。

2-3. 公開と非公開を最初から分ける

情報誰が見られるか
メールアドレス本人と管理者のみ。ビューア・API・ログ・エラー文に出さない。認証と再設定の送信にだけ使う
局 ID（ユーザー名）公開。実名を使わないよう、登録画面で明示する
位置公開するのは丸めた値だけ。丸める格子は緯度・経度とも 0.1°（日本付近で約 9〜11 km）の中心。生の座標はサーバーに保存しない（/setup-id が受け取った時点で丸める）
局の一覧（地図）誰でも見られる。局 ID、丸めた位置、最終受信時刻、状態のみ
観測データ（グラフ・集計）ログインした参加者だけ（決定済み）。生イベントのダウンロードは本人と管理者のみ（推奨。公開するかは §8 の Q-N5）
紹介文（マイページで設定）公開。登録画面で「自宅の住所や学校名を書かない」と明示する
/setup-id のコメント・装置ラベル非公開（本人と管理者のみ）。上の赤枠の理由による
注意：約 10 km の格子でも、周辺に局が 1 つしかない地域では、その格子にいる 1 人が特定されうる。ユーザーの決定どおり全員を 10 km に丸めるが、登録画面でこの点を説明し、地図の点は格子の中心に置く（実位置より中心側にずらす）。

2-4. 未成年と個人情報（人が決めること）

メールアドレスを預かり、位置の一部を公開するので、プライバシーポリシー・利用規約・保護者の同意の取り方が必要になる。これは法的な判断を含むので、計画では「画面に出す場所」と「同意の記録を残す仕組み」だけを用意し、文面と運用は加速キッチンの責任者が決める（§8 の Q-N2）。

  • 登録画面に、収集する情報、公開される情報、削除の方法を書く。
  • 同意した日時と、同意した文面の版を記録する。
  • アカウント削除（メール・位置・観測データを消す）と、本人データの書き出しを、マイページから実行できるようにする。
  • メールは認証と再設定にだけ使い、お知らせなどの別目的には使わない。

4. API の範囲

4-1. Console 互換（Phase 1）

§2-1 の 4 つのエンドポイント。加えて次を守る。

  • CORS ミドルウェアを、本文パーサ・静的配信・認証・各ルートよりも前に置く。成功・401・404 を含むすべての応答に付け、OPTIONS には 204 を返す。Allow-Credentials は付けない。
  • CORS の * は、Console が使う API に限る。登録・マイページなどの同一オリジンのページは Bearer をメモリに置くだけで、Cookie を使わない。
  • /setup-id は、自分の局にだけ許し、何度でも成功する。GPS は受け取った時点で 0.1° の格子に丸め、生の値は保存しない。コメントと装置ラベルは非公開で保存する（§2-1 の赤枠）。
  • /upload-data/:id は、本人の局にだけ許す。受理するフィールドは旧 Console の全フィールドを JSONL に残す（vol は計算値であることも記録）。
  • レート制限は、Console の並列送信（4 並列）を通せる値にする。
  • 重複：互換 API は 1 件 1 POST で、タイムアウト後に再送される。Console は接続ごとに新しい run_id（UUID）を作る（core.js:373。再接続では変わらない）が、ボードが再起動するとイベント番号 event は 0 に戻る。このため、重複の判定は event 単独ではなく (局, run_id, event, time) の組にする。推奨は、この組に一意制約をかけて再送を無害にすること（Phase 1 で決める。決めなければ「重複あり」と文書に書く）。
  • 旧クライアントの少ないフィールド（timestamp, adc, vol, deadtime）への対応はしない（旧クライアントは対象外）。Console のペイロードだけを必須とする。

5. 旧データの移行

旧サーバーは読み取り専用にして残し、新サーバーへコピーする。旧側は消さない。 旧クライアント（cosmicwatch-app、Python クライアント）は対象外なので、切り替えるのは Console の利用者だけ。 旧サーバーのログには sendai と test の setup が直近にあるので、切り替えの前に次を行う。

  1. 旧サーバーのログ（output.log）から、直近 30 日に送ってきた局を洗い出す（読み取りのみ。ユーザーが実行）。
  2. その局の持ち主に、切り替え日と、Console の URL 欄を https://cosmicray.accel-kitchen.com に変える手順を知らせる。
  3. 切り替え日に、旧サーバーのデータをもう一度取り込んで差分を埋める（取り込みは何度実行しても同じ結果になる）。
  4. 差分が合ったら、旧サーバーを読み取り専用にする。旧クライアントで送っている人がいれば、この時点で送れなくなることを事前に知らせる。
対象方針注意
アカウント（users.json）bcrypt ハッシュをそのまま取り込む。メールが無いので「メール未登録」の旧アカウントとして入れ、メールの登録と認証を済ませるまでConsole からのログインは 403 にし、応答の error に「https://cosmicray.accel-kitchen.com/claim でメールを登録してください」と書く（Console はログイン失敗時に error の文字列をそのまま表示する。Console にメール登録の画面は無い）。登録は、同じ局 ID とパスワードでログインできる専用ページ（/claim）で行う旧アカウントは、メール登録を済ませるまで公開地図に出さない。パスワードの平文は扱わない
観測データ（.dat、7 カラム）JSONL に変換して取り込む。各行に source: "legacy-import" を付ける日時のタイムゾーン、ADC のビット深度（0–1023 / 0–4095）、deadtime の単位は、旧データでは事後に分からない（server-plan.html の Q-4・Q-9）。局ごとに注記を持たせ、分からないものは「不明」と記録する
局の位置（旧 config.json など）取り込み時に 0.1° の格子へ丸める。旧サーバーが生の GPS を公開していたことも、公開をやめる理由として記録生の座標は新サーバーに持ち込まない
検証先にドライラン（件数・日付範囲・チェックサムの比較）。結果が合ったら本取り込み。取り込みは何度実行しても同じ結果（重複させない）旧データの読み出しには accel-kitchen か root の権限が必要。実行はユーザー

7. 受け入れ基準とテスト

  • 実ブラウザで確認する。次の 3 つのオリジンから、Console でログインし、数イベントを送って、サーバー側のファイルの行が増えることを見る。curl だけの確認は合格にしない（今日は curl では正常に見えた）。
    1. file://（Origin: null）で開いた Console
    2. 新サーバー自身が https://cosmicray.accel-kitchen.com/console/ で配信する Console（同一オリジン）
    3. 別の https オリジンの Console。Console の本番の配信先が分からないので（Q-N10）、決まるまでは、https://accel-kitchen.com 側に置いた試験ページで代用する
  • レート制限の独立：別々の接続元 IP（Apache を通して X-Forwarded-For が異なる 2 つ以上の IP）から、ログインを失敗させ続けても、別の IP のログインが止まらないこと。外から偽の X-Forwarded-For を付けても、制限を逃れられないこと（VPS 上で、Apache 越しに実際に試す。localhost の試験では、接続元が常にループバックなので、この項目は確かめられない）。
  • イベントの出どころ：Console のデモのイベントは送信キューに入らない。手元の V2 ボード（COM62、FW 2.0.0）をつなぐか、Console の eventToLegacyPayload と同じ形のイベントを送る試験スクリプトを使う。
  • 契約テスト（リポジトリに入れる）：互換 API の 4 エンドポイントについて、成功、400（永久に不正）、401/403（再認証）、429/5xx（再送）、OPTIONS の 204 と CORS ヘッダを、成功・失敗の両方の応答で確かめる。server-plan.html にある「自動テスト 48 件」は手元で見つからないので、これを新しい基準にする。
  • プライバシーのテスト：公開 API のどの応答にも、メール・生の座標・パスワードのハッシュが含まれないこと。登録直後の局は、メール認証が済むまで地図に出ないこと。
  • 復元のテスト：バックアップから別の場所へ復元し、ログインとデータの閲覧ができること。

#問いなぜ判断が必要か
Q-N1認証メールの送信方法：VPS に Postfix を入れるか、外部のメール送信サービスを使うか DNS の現状（2026-11-21、公開 DNS で確認）：MX は Google Workspace、SPF は v=spf1 ip4:118.27.30.120 include:_spf.google.com include:_spf.prtimes.jp ~all（VPS の IP がすでに入っている）、DMARC は p=none。DKIM は Value-Domain の DNS に google._domainkey（Google Workspace のもの）がある。VPS から送る場合の DKIM は無い。
選択肢：
(a) VPS の Postfix：SPF は通る。DKIM の署名（OpenDKIM）と、VPS の逆引き（PTR）の設定が要る。費用なし。届きやすさの調整が必要。
(b) Google Workspace の SMTP（アプリ専用パスワードか SMTP リレー）：すでに使っているので届きやすく、送信は 1 日あたりの上限がある。参加者のメールは Google を通る（受信側も Google のため）。
(c) 外部のメール送信サービス：届きやすいが、参加者のメールが別の事業者を通るので、ポリシーに書く必要がある。
どれでも、差出人は noreply@accel-kitchen.com（親ドメイン）にすると、既存の SPF・DMARC がそのまま使える。cosmicray.accel-kitchen.com を差出人にすると、サブドメイン用の SPF が別に要る。
